How the self-healing bug loop works

beatass · written 15 August 2026

Somebody hits a bug. Without anybody being woken up, that turns into a written case, a verdict, a GitHub issue, a fix with proof it works, and an email telling that person it is fixed. This page explains every step, what is real today, and where a human still has to say yes.

Read this first. Roughly half of what follows is running code you can use right now; the other half is designed and specified but not yet built. Every section is marked BUILT or NOT YET. Nothing on this page sends an email, opens a GitHub issue, or changes any code today.

Step 1. How the report is sent BUILT

The page carries a 3 KB stub that is always awake. It does two things and nothing else: it keeps the last 40 error messages in an array, and it draws the Report a problem button. The real reporter — the sheet, the picker, the screenshot tool — is a separate 52 KB file that is only downloaded the first time somebody actually presses that button.

That split exists for a specific reason. If the reporter only started listening when you opened it, it would have already missed the error you opened it about. And if it were baked into the page, every visitor would pay for a panel that almost nobody opens.

The scrubbing pipeline

Screenshots are a special case. Once the page is pixels, no text scrubber can reach into it. So the masking happens to the page: data-capturing goes on <html>, the stylesheet hatches out every private field, we wait two animation frames for that to actually paint, and only then rasterise. The wait is not fussiness — rasterising in the same frame photographs the page as it looked before the mask landed.

Step 2. How it is received and stored BUILT

The browser posts to /api/bug on the existing Cloudflare Worker. That route is deliberately suspicious of its own client.

Why check 5 refuses instead of cleaning. The browser already scrubbed everything. If a signed token still shows up here, that means the client-side scrubber did not run — probably a stale cached script. Quietly cleaning it would hide a broken safety net. Refusing it, loudly, means we find out.

The case file

One row in a new bug_reports table is the case. It carries the report, the verdict, the issue, the pull request and whether the reporter has been told. So "what happened to report X" is one query, never a hunt through logs.

Step 3. How it is read NOT YET

A small script on your laptop wakes on a timer, picks up cases in received, and asks a model to classify each one. It runs read-only: no GitHub, no email, no ability to change a single file. Reading and doing are separate jobs held by separate processes.

The failure that actually hurts is a confident user_error on a real bug. You tell somebody "that is not a bug", close it, and they never report anything again. So the two verdicts that produce a dismissive reply carry the highest confidence bar, and every one of them is logged for you to skim. When in doubt the machine is required to be unsure.

Step 4. How the GitHub issue is created NOT YET

This is where the two hard constraints live.

  1. Your repository is public. github.com/luv-jeri/beatass is open to the internet. So the issue body can only ever contain a sanitised summary: what broke, on which page, which error, which browser. Never the raw capture, never a screenshot of somebody's screen, never the reporter's address, never a /m link.
  2. Opening an issue is an outward action. Under your own rules, nothing leaves the system without your yes. So the machine writes the issue as a draft and stops.

Step 5. How the fix and the PR are made NOT YET

An agent that writes patches from bug reports with no proof is a machine for producing plausible-looking wrong code at scale. So the fixer is not allowed to open a pull request on confidence. It has to show its working.

The gate: no pre-fix failure evidence, no PR

Why a path allowlist would not work here. The obvious cage is "the agent may only edit these files". It is useless in this codebase: src/index.js is one file containing sending, inbound mail, admin login, private message views and blocking. Allow it and the agent can change anything that matters; forbid it and almost no real bug is fixable. So the cage is capability, not path — the fixer simply does not hold the powers listed above.

One more thing that has to be true first

main has no branch protection today, and a push to main deploys to the live site automatically. So a merged agent PR would ship the same minute. Turning on branch protection is a five minute change and it must happen before the fixer is ever allowed to open a real PR. You have chosen to do it last — that is fine, as long as it lands before that switch.

Step 6. How the person finds out NOT YET

Being told "it is fixed" has to mean it is actually live, not merely merged. So the case only reaches shipped when the deployed commit is confirmed in production — not when the PR closes. Then, and only then, the reporter gets the last of the four emails.

WhenWhat they get
the moment it arrives"Thank you, we have it" plus a reference code
triage says real bug"It is a real issue, we are working on it"
triage says not a bugan actual explanation of how to do the thing
proven live"The problem you reported is fixed"

An attacker must not be able to type a stranger's address into the reply box and make your product email them. So replies are rate limited, carry only fixed product copy, and never contain a word the reporter wrote.

Where it stands today

What you can do right now

Run npx wrangler dev --local --port 8899 from the project, open http://127.0.0.1:8899, and file a report. Then read it back:

npx wrangler d1 execute beatass-db --local --command "SELECT id, state, kind, note FROM bug_reports ORDER BY ts DESC LIMIT 5"

Every claim on this page about built behaviour is backed by a test in bugreport/. The design behind the unbuilt half, including the argument that shaped it, is in PLAN-SELFHEAL.md and PLAN-SELFHEAL-SOL.md.

D. Trust boundaries

Four boundaries, each with a different assumption about who is lying.

BoundaryAssumptionEnforcement
Browser → WorkerThe client may be stale, modified, or hostile Same-origin check, size cap before parsing, rate limit before parsing, and a second scrub check that refuses rather than cleans
Public → /adminAnyone may knock HMAC-signed cookie, constant-time compare, HttpOnly + Secure + SameSite=Lax, 10 attempts per 15 min, fails closed when the secret is absent
Case store → GitHubThe repository is public and permanent Only a sanitised summary may cross. Never the raw capture, a screenshot, a reporter address, or a /m link. A human clicks
Agent → productionAn agent will eventually be confidently wrong No merge, no push, no deploy, no secrets, no live database. Worst case is a draft nobody merges

E. Privacy, as layers

No single mechanism is trusted. Five independent things must all fail before a confession escapes.

What is deliberately NOT protected. The character counter stays visible in a screenshot, so the length of a confession leaks. Left alone on purpose: it is harmless and it is genuinely useful when a bug turns out to be length-related. Named here so it is a decision on the record, not an oversight.

The layering is deliberate. The unit suite was fully green at the moment the browser suite found a confession leaving in a log line — because the rules were right and the wiring was not. A test that cannot see the real bytes cannot tell you that.

Every non-trivial rule here has a mutation control. Redaction was deliberately disabled to confirm the suite went red (9 failures), then restored to confirm it went green again. A check that cannot fail is not a check.
